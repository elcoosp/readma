# Content files

In Readma v2 the readme text never lives inside the config. Every section body
is a markdown file inside the **content directory**, `readma/` by default:

```
readma.yaml
readma/
  about.md
  features.md
  getting-started.md
  installation.md
  usage.md
  roadmap.md
  contributing.md
  acknowledgments.md
  faq.md              <- a custom section, just another file
  20-benchmarks.md    <- a custom section with an explicit order
  header.md           <- optional, rendered after the badges
  footer.md           <- optional, rendered before the markdown refs
```

Everything is optional: a missing file simply means the section is omitted.
A project with a single `readma/about.md` already renders a complete readme.

## Builtin sections

These file names map to well known sections. Each has a default render order
and a default title:

| File                   | Default title    | Default order | Notes                                             |
| ---------------------- | ---------------- | ------------- | ------------------------------------------------- |
| `about.md`             | About            | 10            | Embeds the screenshot and the workspace members table |
| `features.md`          | Features         | 20            |                                                   |
| `getting-started.md`   | Getting started  | 30            |                                                   |
| `installation.md`      | Installation     | 40            | Auto-generated from the language + registry when absent |
| `usage.md`             | Usage            | 50            |                                                   |
| `roadmap.md`           | Roadmap          | 60            | Appends an "open issues" link to the body         |
| `contributing.md`      | Contributing     | 110           | Falls back to a default text when only a code of conduct exists |
| `acknowledgments.md`   | Acknowledgments  | 130           |                                                   |

Two sections are generated by the engine and have no file:

| Id              | Default title | Default order | Source                                    |
| --------------- | ------------- | ------------- | ----------------------------------------- |
| `contact`       | Contact       | 120           | Rendered from `contact` / `author` config |
| `license`       | License       | 140           | Rendered from `license` config            |

Custom sections default to order 100, between roadmap and contributing.

## Custom sections

Any other `.md` file inside the content directory becomes a custom section.
The section id is the file name without extension, and the default title is
the id with dashes and underscores turned into spaces (`my_cool_section.md`
renders as "My cool section").

## Front matter

Each content file accepts a small YAML front matter block:

```md
---
title: Frequently asked questions
order: 30
hide: false
---
The body of the section.
```

| Field   | Type      | Effect                                                        |
| ------- | --------- | ------------------------------------------------------------- |
| `title` | `string`  | Overrides the default title of the section                     |
| `order` | `number`  | Overrides the render order                                     |
| `hide`  | `boolean` | Omits the section from the readme                              |

## Ordering with numeric prefixes

Prefixing a file name with `NN-` sets its order, like
[`30-faq.md`](#front-matter) above. The prefix is stripped from the section
id, so `30-faq.md` and `faq.md` are the same section: when both exist, the
first file name wins (and `validate` warns about the duplicate).

## Header and footer files

`header.md` and `footer.md` are special: they are not rendered as sections
and do not appear in the table of contents. The header body renders right
after the badge row, the footer body right before the repobeats image and the
markdown reference links.

## Retitling or hiding from the config

The `sections` config key overrides any section by id, which is handy for
generated sections or when you do not want to touch the front matter:

```yaml
sections:
  license:
    title: Legal
  roadmap:
    hide: true
```

Config overrides win over front matter, which wins over the defaults.

## Workspace member overrides

Inside a workspace, each member package can hold its own `readma/` directory.
The member content is merged over the root content: files with the same id
replace the root version, member-only files are appended. The root readme
only uses the root content directory.

`installation.md` is the exception: it is package specific, so a root
installation file stays on the root readme and members get their own file or
the auto-generated install snippet.
